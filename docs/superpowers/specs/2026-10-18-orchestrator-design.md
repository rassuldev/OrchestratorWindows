# Orchestrator — дизайн и план

## Context

Пользователь хочет личный инструмент: даёшь подробную задачу («сделай веб-сайт», бот, API — любой софт), и оркестратор доводит её с нуля до рабочего проекта на Маке. Повод — три боли при работе с Claude Code напрямую на больших задачах:
1. **останавливается на полпути** («продолжить?»), приходится сидеть рядом;
2. **качество хромает** — «готово», а на деле не проверено, баги;
3. **теряет контекст** на длинной задаче.

Папка `/Users/qwerty/projects/Orchestrator` пустая. На машине: `claude` CLI 2.1.251, Node 24.8, Python 3.14, Docker.

## Решения пользователя

- Для себя, один пользователь, локально.
- «Готово» = **рабочий проект локально**: папка под git, тесты зелёные, запускается одной командой, отчёт о сделанном. Деплой — не нужен.
- Участие — **чекпоинты по этапам** (требования, план/дизайн, промежуточный показ). Между ними — сам.
- «Руки» — **Claude Code CLI** в headless-режиме (`claude -p`), на подписке пользователя.
- Интерфейс — **локальная веб-панель**.
- Область — **любой софт** (не только сайты).
- Безопасность — **на Маке, в границах папки проекта**: правки файлов и типовые команды разрешены; опасные (`rm -rf`, `sudo`, `git push`, запись вне папки) запрещены.
- Инструменты — **пакеты + сеть, без Docker**: npm/pip и их кэши, интернет разрешены; Docker и `brew install` — нет. БД только встраиваемые (SQLite и т.п.) — это правило зашивается в промпт architect.
- Ключи/секреты — **спрашивать на чекпоинте A**: analyst перечисляет нужные ключи, панель показывает поля-пароли, значения пишутся в `.env` проекта (в `.gitignore`), маскируются в логах и панели; verifier проверяет на реальных сервисах.
- Проверка — веб/API/CLI/боты полноценно **плюс iOS-симулятор**: сборка `xcodebuild`, запуск в симуляторе, скриншоты. Прочие десктоп-GUI/игры — сборка и юнит-тесты.
- Анти-цели (поморщился бы): **непрозрачность** (непонятно, что делает и почему), **шаблонный «ИИшный» результат**, **нельзя продолжить** после падения/сна Мака.

## Цели / не-цели

**Цели:** довести задачу до проверенного рабочего результата без «продолжай»; прозрачность каждого шага и решения; возобновление с места остановки; не-шаблонный дизайн для проектов с UI.

**Не-цели v1:** деплой, мульти-пользователь/авторизация, другие модели кроме Claude, облако, параллельный запуск нескольких проектов (одна очередь — моё решение), Docker-песочница.

## Ключевая идея

**Этапами управляет код (детерминированная машина состояний), а не модель.** На каждый шаг запускается **свежий** `claude -p` с узкой ролью; результат проверяется программой. Цикл не завершается, пока критерии приёмки не выполнены → нет «остановился на полпути». Вся память проекта — **в файлах** проекта, каждый агент стартует с чистого листа и читает их → нет потери контекста.

## Пайплайн проекта

```
intake → [analyst: вопросы] → ✋A ответы → [analyst: spec.md] → ✋B утвердить spec
      → [architect: architecture.md + plan.json] → [designer: 2–3 разных макета, только если есть UI] → ✋C утвердить план + выбрать дизайн
      → цикл по задачам: [implementer] → [verifier] → [reviewer] → (fail → назад к implementer, ≤3 попытки → ✋ «нужна помощь»)
      → после milestone «MVP» → ✋D демо: приложение запущено, ссылка + скриншоты, замечания → новые задачи
      → [finalizer: полный прогон, README, команда запуска, REPORT.md] → done
```

На любом чекпоинте: «Одобрить» или «Поправить» (текст комментария → тот же агент переделывает с учётом комментария).

**✋ «Нужна помощь»** (моё решение): варианты — подсказка + повторить задачу; пропустить задачу; «исправил руками — продолжай». Возврата к уже утверждённым spec/плану в v1 нет (машина состояний линейная); замечания на демо D превращаются в новые задачи в конце плана.

**Уведомления** (моё решение): macOS-уведомление (`osascript display notification`) + бейдж в панели, когда ждёт чекпоинт или «нужна помощь», и когда проект готов.

### Роли (промпты в `prompts/<role>.md`, подаются через `--append-system-prompt`)
- **analyst** — уточняющие вопросы (`questions.json`), затем `spec.md` (цели, функции, критерии приёмки, не-цели).
- **architect** — стек, структура, `architecture.md`; `plan.json`: milestones → tasks, у каждой задачи `acceptance` (критерии) и `verify` (команды проверки); один milestone помечен `mvp: true`. Обязательно задача №1 — скелет + тестовый раннер + команда запуска.
- **designer** (если в проекте есть UI) — 2–3 **заметно разных** направления как статичные HTML-макеты + скриншоты; явный запрет на шаблонные «ИИшные» решения. Агенту доступны пользовательские скиллы (напр. `impeccable`), т.к. CLI запускается не в `--bare`.
- **implementer** — одна задача: код + тесты, коммит `task-<id>: …` по завершении.
- **verifier** — запускает `verify`-команды и тесты, поднимает приложение; для веба делает скриншоты (desktop + mobile) helper-скриптом и смотрит их; для iOS — `xcodebuild` под симулятор, `xcrun simctl` boot/install/launch, скриншот helper-скриптом; пишет `verdict.json` {pass, issues[]}.
- **reviewer** — смотрит diff задачи против spec и критериев; `verdict.json`.
- **finalizer** — полный прогон, README, `REPORT.md` (что сделано, как запустить, известные ограничения).

Каждый агент **обязан** дописать в `decisions.md` значимые решения с «почему» (против непрозрачности).

### Файлы проекта (память)
`<workspace>/<slug>/` — сам проект (git). Служебное — в `<slug>/.orchestrator/`:
`task.md` (исходная задача), `questions.json`, `spec.md`, `architecture.md`, `plan.json`, `design/`, `decisions.md`, `state.json`, `logs/<step-id>.jsonl`, `screenshots/`, `verdicts/`. `.orchestrator/` добавляется в `.gitignore` проекта (моё решение; спек/план можно копировать в `docs/` проекта на финале).

Программа валидирует все JSON-выходы (zod). Невалидно → один перезапуск агента с текстом ошибки, потом ✋.

### Запуск агента
`spawn('claude', ['-p', prompt, '--output-format','stream-json','--verbose', '--append-system-prompt', rolePrompt, '--permission-mode','acceptEdits', '--allowedTools', …, '--disallowedTools', 'Bash(rm -rf*)','Bash(sudo*)','Bash(git push*)', …, '--settings', <json c sandbox>], {cwd: projectDir})`
- Ограничение «в границах папки»: встроенный sandbox Claude Code (`sandbox.enabled` в settings, на macOS ограничивает запись bash-команд текущей папкой) + списки allow/deny. Дополнительно разрешить запись в кэши пакетных менеджеров (`~/.npm`, `~/Library/Caches/*` для pip/Playwright) и `~/Library/Developer` (DerivedData/симулятор для iOS), сеть — открыта; `docker*`, `brew install*`, `sudo*`, `git push*`, `rm -rf*` — deny. Точные флаги/ключи — проверить на установленной версии CLI (задача билдера, `claude --help` и доки).
- Секреты из `.env` маскируются (замена значений на `***`) в `logs/*.jsonl` и SSE.
- События stream-json → `logs/<step>.jsonl` + SSE в панель; из финального `result` берём `session_id`, длительность, usage.
- Таймаут на шаг (по умолчанию 45 мин). Ошибка лимита/ратлимита подписки → пауза с бэкоффом и автоповтор, а не падение.

### Возобновление
`state.json` пишется атомарно после каждого перехода. При старте сервера проект в статусе `running` продолжает с текущего шага: прерванный шаг перезапускается с пометкой «предыдущая попытка прервана — сначала осмотри рабочее дерево и `git status`». Кнопки Пауза/Продолжить. Пока идёт работа — держим Мак бодрым через `caffeinate -i` (дочерний процесс).

### Веб-панель (localhost:4321)
- Список проектов + «Новый проект» (поле задачи, имя).
- Страница проекта: таймлайн этапов/задач (роль, статус, длительность, попытка), **живой лог** текущего агента (текст ассистента + краткие вызовы инструментов), вкладки spec / plan / decisions / screenshots / report.
- Чекпоинт: что нужно (вопросы-форма / документ / макеты на выбор / ссылка на запущенное приложение), кнопки «Одобрить» / «Поправить».

## Стек оркестратора (мои решения)
Node 24 + TypeScript, Fastify (API + SSE + раздача UI), React + Vite для панели, zod для схем, Playwright (chromium) для скриншот-helper'а, vitest для тестов. Хранилище — только файлы (без БД): прозрачно и легко читать руками. Workspace по умолчанию `~/orchestrator-projects/` (настраивается в `config.json`).

## Порядок реализации
1. `git init`, сохранить этот дизайн в `docs/superpowers/specs/`, скелет TS-проекта, vitest.
2. `runClaude.ts`: запуск, парсинг stream-json, таймаут, отмена, детект ратлимита. Тесты на фейковом `claude`.
3. `schemas.ts` + `store.ts` + `stateMachine.ts`: все состояния/переходы, атомарная запись, возобновление. Тесты переходов (включая ретраи ≤3 и ✋).
4. `prompts/*.md` — промпты ролей с чёткими контрактами выходных файлов.
5. Сервер: API (create/list/get project, approve/revise checkpoint, pause/resume), SSE логов; восстановление `running`-проектов при старте; caffeinate.
6. Панель: список, таймлайн, живой лог, формы чекпоинтов, просмотр документов и скриншотов.
7. `screenshot.ts` + подключение к verifier/designer; секреты на чекпоинте A + маскирование; уведомления.
8. `simshot.ts` (iOS-симулятор) + ветка verifier для iOS.
9. Догфудинг: реальный прогон небольшой задачи (напр. «todo-приложение с бэкендом») через весь пайплайн, правка промптов по результатам; затем маленькое iOS-приложение.

После одобрения: детальный пошаговый план через superpowers:writing-plans, затем реализация.

## Проверка
- `npm test` — unit (машина состояний, парсер stream-json, схемы) и e2e пайплайна с фейковым `claude`: проект проходит все этапы, чекпоинты ждут одобрения, ретраи работают, kill сервера посреди шага → после рестарта продолжает с того же шага.
- Ручная: `npm run dev`, открыть панель в браузере, создать проект с реальной небольшой задачей, пройти чекпоинты A–D, убедиться: в конце папка под git, тесты проекта зелёные, приложение запускается командой из README, есть REPORT.md и decisions.md.
- Прерывание: закрыть сервер посреди сборки, запустить снова — работа продолжилась.
