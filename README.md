# Orchestrator для Windows

Windows-версия [Orchestrator](../Orchestrator). Отличия от macOS-версии собраны в разделе «Отличия от macOS-версии» в конце.

Личный локальный оркестратор: вы даёте подробную задачу («сделай сайт», бота, API, CLI, десктоп-приложение), а он доводит её с нуля до рабочего проекта на вашем ПК с Windows. Этапами управляет код (детерминированная машина состояний), а не модель: на каждый шаг запускается свежий `claude -p` с узкой ролью, а память проекта хранится в файлах. Поэтому нет «остановился на полпути», потери контекста и невозобновляемых прогонов. Интерфейс — локальная веб-панель.

## Требования

- Windows 10/11 (уведомления и запрет сна идут через встроенный Windows PowerShell).
- Node.js >= 24.
- [Git for Windows](https://git-scm.com/download/win): каждый проект — git-репозиторий, а Claude Code на Windows выполняет команды агентов в Git Bash.
- Claude Code CLI (`claude.exe`, нативный установщик), в котором выполнен вход. Проверка (PowerShell):
  ```powershell
  claude -p "reply OK" --output-format json
  ```
  В ответе должно быть `"is_error": false`. Если пишет, что OAuth истёк, выполните `claude`, затем `/login`.
  Если Claude Code установлен через npm (`claude.cmd`), укажите в `config.json` путь к его `cli.js`:
  `"claudeBin": "C:/Users/<вы>/AppData/Roaming/npm/node_modules/@anthropic-ai/claude-code/cli.js"`. `.cmd` нельзя запустить без оболочки, которая испортила бы многострочный промпт.

## Установка

```powershell
npm install
npx playwright install chromium   # для скриншотов (verifier, designer)
```

Если репозиторий клонирован через git, `.gitattributes` сохранит LF-окончания у `bin/orch-shot` (его запускает Git Bash). Если копируете папку иначе, проверьте, что в этом файле нет CRLF.

## Запуск

```powershell
npm start        # собирает панель и поднимает сервер: http://127.0.0.1:4321
npm run dev:web  # разработка панели через Vite (проксирует /api на :4321, сервер должен быть запущен)
```

Сервер слушает только `127.0.0.1`, одновременно выполняется один проект (одна очередь).

## Как идёт проект

```
intake → analyst: вопросы → A → analyst: spec → B → architect: plan
      → designer (только если есть UI) → C → цикл по задачам → D (демо MVP) → finalizer → done
```

В цикле на каждую задачу: `implementer` → `verifier` → `reviewer`. При провале шаг возвращается к implementer с замечаниями (до 3 попыток на задачу, на остальных шагах до 2).

- **Не блокирующие замечания не теряются.** verifier и reviewer пишут их в поле `notes` вердикта, оркестратор дописывает их в `.orchestrator/followups.md` чек-листом. Следующие implementer'ы исправляют то, что касается их задачи, и отмечают `[x]`; reviewer проваливает задачу, если положенный ей пункт не исправлен, а дефект, который «исправит потом» ни одна задача плана, не считается замечанием. Открытые пункты finalizer переносит в REPORT. В панели они на вкладке «Замечания».

Чекпоинты, где ждут вас (уведомление Windows и бейдж в панели):

- **A — ответы:** форма с вопросами analyst; здесь же поля для секретов (API-ключи).
- **B — spec:** «Одобрить» или «Поправить» (комментарий, агент переделывает).
- **C — план (и дизайн):** одобрить план, при UI выбрать один из 2–3 макетов, либо поправить.
- **D — демо MVP:** скриншоты проверки; приложение запускается кнопкой «Запустить приложение» (появится ссылка) и останавливается само, когда вы продолжаете (а также при паузе и перед любым следующим шагом), чтобы не держать порт и базу. Замечания превращаются в новые задачи в конце плана.

**«Нужна помощь»** появляется, когда попытки закончились или шаг упал. Варианты:

- повторить шаг (можно с подсказкой);
- пропустить задачу (только на этапе сборки);
- «исправил руками — продолжай» (ваши правки коммитятся как `task-<id>: manual fix by user`, сборка продолжается с проверки, ревью видит и их).

Роли и их промпты лежат в `prompts/` (`_common.md` — общие правила для всех).

## Существующий проект

В форме нового проекта можно указать абсолютный путь к локальному git-репозиторию. Тогда оркестратор не начинает с нуля, а клонирует его (с историей, без `origin`) в `%USERPROFILE%\orchestrator-projects\<slug>\`, дописывает `.orchestrator/` и `.env` в `.gitignore` и дальше идёт по обычному пайплайну, достраивая то, что есть. Оригинал не меняется; репозиторий должен быть без незакоммиченных изменений. Забрать результат обратно:

```powershell
git -C C:\path\to\original pull $env:USERPROFILE\orchestrator-projects\<slug> <branch>
```

## Где что лежит

Проекты — в `%USERPROFILE%\orchestrator-projects\<slug>\` (обычный git-репозиторий).

```
<slug>/
  README.md, REPORT.md   # пишет finalizer: как запустить, что сделано, ограничения
  .env                   # секреты с чекпоинта A (в .gitignore)
  .orchestrator/         # служебное, в .gitignore проекта
    task.md  questions.json  answers.json  spec.md  architecture.md  plan.json
    decisions.md         # решения агентов с «почему»
    followups.md         # не блокирующие замечания проверяющих, чек-лист
    state.json           # состояние пайплайна (атомарная запись после каждого перехода)
    design/  logs/<step>.jsonl  screenshots/  verdicts/
```

Значения из `.env` маскируются (`***`) везде, куда может попасть вывод агентов: в логах шагов и событиях панели, в `state.json` (ошибки, замечания проверки) и в документах и текстовых файлах, которые отдаёт панель (spec, README, макеты, вердикты).

## Что разрешено агентам

Каждый агент запускается с `--settings`, собранным в `src/agents/settings.ts`.

**Песочницы нет.** OS-sandbox Claude Code работает только на macOS, Linux и WSL2, на нативной Windows его нет. Поэтому sandbox явно выключен (`sandbox.enabled: false`), и агентов ограничивают только правила permissions:

- `--permission-mode acceptEdits`: правка файлов (Edit/Write) разрешена только внутри папки проекта. Правка снаружи требует подтверждения, а в `claude -p` его некому дать, поэтому она отклоняется.
- Разрешены любые команды Bash (Git Bash), `WebFetch` и `WebSearch`.
- Запрещено (`deny`): `rm -rf`, `sudo`, `git push`, `docker`, `winget`/`choco`/`scoop`, `npm install -g`, `rd /s`, `rmdir /s`, `del /s`, `format`, `reg`, `shutdown`, `Remove-Item`, чтение и правка `~/.ssh`.
- **Ограничение:** shell-команда агента может писать куда угодно, куда может ваш пользователь. Deny-список ловит только явные шаблоны. Не запускайте оркестратор под администратором. Если нужна изоляция, используйте отдельную учётную запись Windows или macOS/WSL2-версию.
- Коммиты делает оркестратор, а не агенты. Docker не используется, БД только встраиваемые (SQLite и т.п.).
- verifier и reviewer только проверяют: если они оставили изменения в файлах проекта, оркестратор их откатывает (`.env` и `.orchestrator/` не трогает) и возвращает задачу implementer'у.
- При таймауте, паузе, остановке сервера и после завершения шага убивается всё дерево процессов агента (`taskkill /F`), включая запущенные им dev-серверы. В Windows нет групп процессов, поэтому дерево собирается по `ParentProcessId` (Windows помнит его даже у осиротевших процессов) и раз в 15 секунд снимается снимок, чтобы найти и процессы, чей родитель уже завершился.

Скриншоты агенты делают через `bin/orch-shot` (Git Bash). Для cmd и PowerShell есть `bin/orch-shot.cmd`.

`claude -p` молча игнорирует невалидные `--settings`. Поэтому при старте сервер проверяет форму настроек (режим `acceptEdits`, deny-список на месте) и печатает предупреждение `WARNING: agent settings…`, если что-то не так.

## Конфигурация

Необязательный `config.json` в корне репозитория (в `.gitignore`; образец — `config.example.json`):

| Ключ | По умолчанию | Описание |
|---|---|---|
| `workspace` | `~/orchestrator-projects` (`~` — это `%USERPROFILE%`) | где создаются проекты |
| `port` | `4321` | порт панели и API |
| `claudeBin` | `claude` | `claude.exe` (через PATH или полный путь) либо путь к `cli.js` npm-установки |
| `model` | не задан (модель по умолчанию CLI) | модель для агентов |
| `stepTimeoutMin` | `45` | таймаут одного шага, минуты |

Переменные окружения переопределяют файл: `ORCH_WORKSPACE`, `ORCH_CLAUDE_BIN`. Для тестов: `ORCH_NO_NOTIFY=1` (без уведомлений), `ORCH_NO_KEEP_AWAKE=1` (без запрета сна).

## Возобновление

- Если сервер остановили или ПК уснул посреди шага, после перезапуска проект продолжается с того же шага. Прерванный шаг перезапускается с пометкой сначала осмотреть рабочее дерево и `git status`.
- В панели есть «Пауза» и «Продолжить».
- Лимит подписки (rate limit) — не ошибка: проект ждёт с нарастающей паузой (10, 20, 40, 60 минут) и повторяет шаг сам (с пометкой осмотреть то, что успел сделать прерванный прогон). Если на странице проекта включить тумблер «Пауза при лимите» (рядом с «Пауза»), проект вместо этого встаёт на паузу и присылает уведомление; продолжить — «Продолжить». Включение во время ожидания лимита ставит на паузу сразу.
- Если в самом оркестраторе случилась внутренняя ошибка, проект показывается как «ошибка» с текстом; «Продолжить» повторяет шаг.
- Пока идёт работа, ПК не засыпает: фоновый PowerShell держит `SetThreadExecutionState(ES_SYSTEM_REQUIRED)`. Экран гаснуть может.
- Остановить сервер: Ctrl+C в его окне. Демо-приложения и агенты при этом останавливаются вместе с ним.

## Тесты

```powershell
npm test            # vitest
npm run typecheck   # tsc --noEmit
```

Тесты проходят и на macOS (для разработки). Один тест (агент вышел, а его дочерний процесс остался) выполняется только на Windows: на macOS и Linux осиротевший процесс переходит к pid 1 и по родителю его уже не найти.

## Отличия от macOS-версии

- Нет iOS: убраны платформа `ios`, `orch-sim`, Xcode и Swift в промптах.
- Нет OS-sandbox: агентов ограничивают только правила permissions (см. «Что разрешено агентам»).
- Уведомления — toast через PowerShell вместо `osascript`. Запрет сна — `SetThreadExecutionState` вместо `caffeinate`.
- Процессы агентов и демо-приложений убиваются деревом (`taskkill /F`), а не сигналом группе процессов.
- `runCommand` демо-приложения выполняется через `cmd.exe`, а не `sh`. Архитектор предупреждён об этом в промпте.
- В промптах агентов все пути записаны с прямыми слешами (`C:/Users/...`): их команды выполняет Git Bash.
